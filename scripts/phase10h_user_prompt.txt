# NIYANTRA — Phase 10H: Advanced Conflict Detection & Resolution

**OBJECTIVE:** Build a reliable conflict-resolution system for Niyantra's offline-first, multi-device architecture.

Phase 10H must build on the existing Phase 10A–10G implementation without breaking existing synchronization, offline storage, authentication, or productivity functionality.

## 1. Mandatory Pre-Implementation Audit

Inspect the actual implementation of:

- Phase 10F server synchronization models and APIs.
- Phase 10G push/pull synchronization engine.
- IndexedDB repositories and database schema.
- Sync queue and operation versioning.
- Sync metadata and existing conflict records.
- Entity update and deletion mechanisms.
- Device registration and account isolation.
- Cursor and acknowledgement logic.

Identify existing conflict-related behavior and gaps before implementation.

Do not assume that the previous phase reports guarantee correctness.

## 2. Conflict Detection

Detect conflicts when:

- Two devices modify the same entity while offline.
- One device deletes an entity while another modifies it.
- Two devices modify the same entity before receiving each other's updates.
- A remote update arrives while a local update remains pending.
- Multiple operations for the same entity arrive in different synchronization batches.

Use entity versions and server-side canonical versions wherever possible.

Do not rely exclusively on timestamps.

## 3. Conflict Data Preservation

When a conflict is detected:

- Preserve the local version.
- Preserve the remote version.
- Preserve the original server version.
- Record the originating device for each version where available.
- Record operation IDs and timestamps.
- Record the conflict detection time.
- Prevent either version from being silently discarded.

Create a structured conflict record with an appropriate lifecycle.

Possible states:

- DETECTED
- PENDING_RESOLUTION
- RESOLVED_LOCAL
- RESOLVED_REMOTE
- RESOLVED_MERGED

Adapt these states to the existing architecture where appropriate.

## 4. Conflict Resolution Strategies

Implement the following strategies:

### A. Keep Local
Preserve the local version and synchronize the selected version to the server.

### B. Keep Remote
Replace the local version with the selected remote version after preserving the conflict history.

### C. Manual Merge
Allow the user to combine appropriate fields from both versions.

For example:

Local version:
- Title: Complete ML assignment
- Priority: High
- Due date: November 25

Remote version:
- Title: Complete ML assignment
- Priority: Low
- Due date: November 27

Merged version:
- Title: Complete ML assignment
- Priority: High
- Due date: November 27

Do not assume every field can safely be merged. Handle relationships, deletion state, and structured data carefully.

## 5. Entity-Specific Conflict Handling

Inspect the fields and relationships of each supported entity.

Implement appropriate conflict handling for:

- Tasks
- Goals
- Habits
- Habit logs
- Daily timeblocks
- Daily intents
- Recommendations
- Activity logs

Avoid treating every entity as a simple flat object.

For append-only or historical records, prefer safe deduplication and preservation over destructive replacement.

## 6. Server-Side Consistency

Extend the Phase 10F synchronization backend only where necessary.

Ensure:

- Server entity versions are validated.
- Stale updates are detected.
- Duplicate operations remain idempotent.
- Conflict records are associated with the correct user.
- Devices cannot resolve conflicts belonging to another account.
- Resolved versions are propagated to all registered devices.
- Deletion conflicts preserve tombstones and historical information.

Use database transactions for conflict resolution.

Use Alembic for schema changes and create a backup before modifying the database.

## 7. Frontend Conflict Experience

Integrate conflict handling into the existing interface without redesigning Niyantra.

Provide:

- A visible conflict indicator.
- A list of unresolved conflicts.
- A comparison of local and remote versions.
- Clear device/source information.
- Keep Local action.
- Keep Remote action.
- Merge action where supported.
- A resolved-conflict history.

The user must understand what differs before choosing a resolution.

Do not automatically resolve important conflicts without a clearly defined safe policy.

## 8. Resolution Synchronization

After a conflict is resolved:

1. Save the selected result locally.
2. Create the appropriate outgoing synchronization operation.
3. Submit it to the server.
4. Confirm server acceptance.
5. Propagate the resolved version to other devices.
6. Mark the conflict as resolved.
7. Preserve the resolution history.

Ensure that conflict resolution itself does not create infinite synchronization loops.

## 9. Testing Requirements

Create tests for:

- Two devices updating the same task.
- Local update versus remote deletion.
- Local deletion versus remote update.
- Simultaneous goal modifications.
- Conflicting habit changes.
- Duplicate operation delivery.
- Stale entity versions.
- Manual merge.
- Keep Local.
- Keep Remote.
- Account isolation.
- Device revocation.
- Interrupted conflict resolution.
- Conflict propagation to a third device.
- Restart recovery.
- Historical conflict preservation.

Test using separate IndexedDB instances and a shared backend simulation.

## 10. Data Safety

Mandatory rules:

- Never delete either version before resolution is safely recorded.
- Never reset the existing SQLite database.
- Never discard pending sync operations.
- Never silently overwrite unresolved conflicts.
- Preserve existing user data and relationships.
- Preserve offline functionality.
- Back up databases before schema modifications.
- Keep existing APIs backward-compatible where possible.

## 11. Regression Verification

Run:

- All backend tests.
- All frontend tests.
- Authentication tests.
- IndexedDB tests.
- Sync queue tests.
- Sync manager tests.
- Multi-device synchronization tests.
- Production build.
- Database integrity checks.
- Foreign-key checks.

Report exact results.

## 12. Final Report

Provide:

1. Pre-implementation audit.
2. Conflict detection architecture.
3. Conflict storage schema.
4. Resolution strategies.
5. Server-side validation.
6. Frontend conflict experience.
7. Synchronization behavior after resolution.
8. Files created and modified.
9. Backend test results.
10. Frontend test results.
11. Multi-device conflict scenarios.
12. Database integrity results.
13. Remaining limitations.

Clearly distinguish automated simulations from testing on actual separate devices.

## DEFINITION OF DONE

Phase 10H is complete when:

- Concurrent edits are detected.
- Neither version is silently lost.
- Users can choose or merge versions.
- Resolutions propagate to all devices.
- Deletion conflicts are handled safely.
- Conflict history is preserved.
- Existing offline and synchronization functionality remains intact.

**The guiding principle: Niyantra must protect the user's data even when multiple devices change it independently.**
